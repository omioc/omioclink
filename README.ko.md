## 1. OmiocLink 소개

OmiocLink는 **나와 정해진 친구들만 쓰기 위한** 데스크톱 커뮤니케이션 도구입니다. 공인망에 연결된 작은 Linux 머신에서 시그널링 서비스를 하나 돌리고, 몇 명의 친구가 클라이언트를 설치하면 함께 게임하며 음성 채팅을 하고, 같은 화면을 보고, 같이 음악을 들을 수 있습니다

![ 海报](assets/readme/海报.webp)

두 부분으로 구성됩니다:

| 디렉터리 | 내용 |
| --- | --- |
| `client/` | Flutter 클라이언트: Windows 데스크톱 + Android. iOS는 준비 중이며 도움을 간절히 기다리고 있습니다 |
| `server/` | FastAPI 시그널링 서버 + 자체 개발 STUN + 웹 관리 콘솔. 오프라인 배포용 compose와 이미지 내보내기 스크립트 포함([server/README](server/README.md) 참고) |
| `deploy/` | 서버 온라인 배포에 쓰는 compose: Docker Hub 이미지만 받습니다. 배포 절차는 [server/README](server/README.md) 참고 |

OmiocLink 프로젝트 전체에는 하나의 설계 제약이 관통하고 있고, 모든 기능이 그 위에 세워져 있습니다:

> **서버는 시그널링과 상태만 담당하며 미디어를 절대 중계하지 않습니다.** 음성, 화면, 채팅은 모두 멤버 사이에서 직접 오갑니다(WebRTC + DTLS-SRTP). 서버에는 **미디어 중계 모듈이 없고** TURN도 배포하지 않습니다 —— 서버 트래픽은 언제나 KB 수준입니다

적합한 상황: 2~8명의 고정 소그룹이 함께 게임하고, 영화나 경기를 같이 보고, 심야에 같이 음악을 듣고, 친구의 화면을 원격으로 봐 주면서, 그 데이터가 어떤 서드파티 서비스도 거치지 않기를 바라는 경우

### 2.1 P2P 통신: 미디어는 서버를 거치지 않고, 프록시도 중계도 없습니다

- **메시 구성**: 방에 입장하면 각자가 방 안의 다른 모든 멤버와 PeerConnection을 하나씩 맺습니다. 지연은 단 한 홉입니다. 방 인원 상한은 2~8명으로, 메시 방식이 가장 효율적인 규모입니다
- **서버가 중계하는 것은 세 가지뿐**: SDP(offer/answer), ICE 후보, 방과 멤버 상태입니다. 모두 몇 KB짜리 JSON이며, 미디어는 첫 프레임부터 양쪽 단말 사이로 직접 흐릅니다
- **중계도, "트래픽 프록시"라는 선택지도 없습니다**: 서버에 TURN이 없고 어떤 릴레이 프로세스도 없습니다. 그 대가로 **홀 펀칭에 실패하면 연결되지 않습니다**. 네트워크 환경에 맞춰 사용하세요(서버에서 stun 모드를 켜면 설정에서 현재 클라이언트의 네트워크 모드와 사용 가능 여부를 확인할 수 있습니다)
- **같은 LAN이면 자동으로 내부망으로**: host 후보 덕분에 같은 WiFi에 있는 멤버는 직접 연결됩니다. 지연 5ms 미만, 외부 트래픽 없음
- **네트워크를 넘을 때는 STUN 홀 펀칭**에 의존하며, 업계 경험상 성공률은 약 80~90%입니다(가정용 공유기는 대부분 콘 NAT). 대칭형 NAT(통신사 CGNAT에서 흔함), UDP를 막는 학교·회사 네트워크에서는 실패합니다
- **실패도 분명히 알립니다**: 입장 전에 연결성을 점검하고, 연결되지 않는 멤버는 화면에 표시됩니다. 설정의 「현재 연결」에서 **직접 연결된 멤버 x/y**, 업/다운 비트레이트를 실시간으로 보여 주고, 홀 펀칭에 실패한 멤버가 있으면 실행 가능한 조언(휴대폰 핫스팟으로 전환 / 가정용 회선 변경 / 방화벽의 UDP 차단 여부 확인)을 제시합니다
- **STUN은 직접 구축할 수 있습니다**: `cd deploy && docker compose --profile stun up -d` 로 「당신의 공인 매핑 주소는 무엇인가」에만 답하는 STUN을 띄웁니다. 이것도 미디어를 전혀 중계하지 않습니다

### 2.2 공유 음성

- 입장하면 바로 마이크가 켜지고, 마이크 입력에는 에코 제거 / 노이즈 억제 / 자동 게인 조정(AEC / NS / AGC)이 적용되며 Opus로 인코딩됩니다
- 멤버 목록에는 한 사람당 타일 하나로 발화 레벨, 연결 품질, 음소거 상태가 표시됩니다(음소거 상태는 서버가 방 전체에 브로드캐스트합니다)
- **서로 간섭하지 않는 세 가지 로컬 볼륨**, 모두 자신에게만 영향을 주고 서버에 보고되지 않습니다:
  - 음악 볼륨(0~100)
  - 멤버별 볼륨(0~200, `userId` 기준으로 기억하며 재접속·재입장·재시작 후 자동 복원)
  - 마이크 볼륨(0~100, 기본 녹음 장치의 시스템 볼륨을 직접 조절하는 것으로, 「상대가 듣는 내 목소리 크기」에 해당합니다)
- 출력 장치를 전환할 수 있고(헤드폰 / 스피커), 장치를 꽂거나 빼면 목록이 자동으로 갱신됩니다
- 모바일(**青竹** 테마, 짧은 변 600dp 미만이면 단일 컬럼 + 하단 내비게이션으로 자동 전환)은 동일한 통화 로직을 재사용하며, 오른쪽 컬럼을 하단 패널로 바꾼 것뿐입니다

### 2.3 화면 공유

- **모니터 전체 또는 개별 창**을 선택할 수 있고(썸네일 제공), **시스템 오디오 동시 공유**도 선택할 수 있습니다 —— 공유 중인 게임이나 영화 소리도 함께 전달됩니다(스피커로 재생하면 상대에게 에코가 들릴 수 있으니 헤드폰 사용을 권장합니다)
- 세 단계 **인코딩 전략**을 공유하는 내용에 맞게 선택합니다(기본은 「균형」이며 스스로 판단합니다):

| 프리셋 | 적합한 용도 | 프레임레이트 | 대역폭이 부족할 때 |
| --- | --- | --- | --- |
| 프레임레이트 우선 | 게임 화면 공유 | 60fps 고정(30 미만으로 내려가지 않음) | 해상도를 먼저 낮추고 프레임레이트는 유지 |
| 해상도 우선 | 회의 / 문서 / 발표 | 30fps에서 시작, 여유가 있으면 60까지 상승 | 소스 해상도 고정, 스케일링 없음 |
| 균형 | 일반적인 상황 | 자동(30 / 60) | 평균 QP로 화면이 고동적·정적인지 판단해 어느 쪽을 지킬지 결정 |

- **비트레이트는 직접 조정할 필요가 없습니다**: 30 Mbps 업링크 예산을 시청자 수로 나눕니다(2K 소스 + 시청자 3명 ≈ 스트림당 9 Mbps). 예산에 따라 해상도와 프레임레이트가 자동으로 한 단계씩 내려가며, 하한은 **720p / 30fps** —— 게임 화면 공유에서는 프레임 드랍이 흐려지는 것보다 더 견디기 어렵습니다

- 시청 측은 원클릭 전체 화면(Esc로 종료), 공유자는 언제든 중지하거나 소스를 바꿀 수 있습니다
- 방 페이지의 오른쪽 컬럼은 「화면 공유 + 채팅 + 대기열」이며, 채팅 메시지는 **DataChannel**(P2P)로 전송됩니다. 서버는 어떤 채팅 내용이나 기록도 저장·중계하지 않습니다
- Android에서는 화면 공유를 제공하지 않습니다(`getDisplayMedia`의 Android 구현이 없음). 마이크 시스템 볼륨 조절도 아직 제공되지 않을 수 있습니다

### 2.4 곡 신청 스테이션(**MusicFree 호환**)

곡 신청 스테이션의 음원은 내장이 아니라 **MusicFree 플러그인을 실행**하는 방식입니다:

- 서버는 **플러그인 구독 주소**만 저장하고, 오디오와 음악 메타데이터는 전부 **각 클라이언트가 로컬에서** QuickJS 샌드박스로 플러그인을 실행해 얻습니다 —— 서버는 어떤 오디오도 프록시·캐시·전송하지 않습니다
- MusicFree와 1:1로 대응하는 세 가지 뷰: **검색**(상단 검색창, 유형 × 음원 2단 탭, 입력하는 대로 결과 표시), **랭킹**, **인기 플레이리스트**
- 음원마다 개별 타임아웃(모든 음원 2초 / 특정 음원 8초 / 차트 4초)을 적용하고, 3회 연속 실패하면 5분간 서킷 브레이커가 동작합니다. 실패는 메인 화면을 차지하지 않고 검색창 옆에 「N개 음원 이상」이라는 작은 진입점만 남깁니다
- 검색 결과는 6시간 동안 로컬에 캐시됩니다. 설정에서 플러그인 활성화·비활성화·정렬·삭제, 전체 업데이트, `userVariables` 설정, 음질 선택(부드러움 / 표준 / 고음질 / 무손실)이 가능합니다
- **적절한 음원 플러그인을 설치하면** 이론상 여러 앱을 오갈 필요 없이 대부분의 음악을 들을 수 있습니다. 다만 실제 품질은 설정한 플러그인의 품질에 달려 있습니다

### 2.5 함께 음악 듣기 (방 공동 재생)

방에서의 재생은 "각자 따로 재생"이 아니라 **서버 권위 + 시계 정렬**로 동작합니다:

- 대기열은 서버가 보유하고, 변경될 때마다 스냅샷 전체를 브로드캐스트합니다(`revision`은 단조 증가). 누가 신청했는지, 몇 번째 곡인지, 누가 곡을 넘겼는지가 모든 클라이언트에서 동일하게 보입니다
- **재생 진행은 시계 동기화에 기반합니다**: 클라이언트는 ping/pong으로 SNTP 방식 오프셋을 추정하며(RTT가 가장 작은 샘플만 유지하고 서버 시계만 신뢰), 각자 "재생을 시작한 시각"으로 추측하지 않습니다
- **권한에는 경계가 있습니다**: 곡 신청은 누구나 가능(1인당 대기열에 기본 88곡). 곡 넘기기는 방장 또는 현재 곡을 신청한 사람만 가능하고, 대기열 비우기는 방장만 가능합니다. 클라이언트는 권한 없는 버튼을 숨길 뿐이며, 서버가 최종 판정을 한 번 더 합니다
- 한 곡이 끝나면 자동으로 다음 곡으로 넘어갑니다(클라이언트가 EOS를 보고하고 서버는 `revision` 기준으로 멱등 처리)
- **재생 모드는 방 단위**입니다: 목록 반복(기본) / 한 곡 반복 / 순차 재생 / 셔플. 재생·일시정지 버튼 왼쪽 버튼으로 순환 전환하며, 방의 모든 사람이 같은 모드를 봅니다. 모드를 바꿔도 재생 중인 곡은 끊기지 않습니다
- 가사는 LRC 타임라인에 맞춰 로컬 재생 진행에 따라 스크롤됩니다. 가사를 가져올 수 없으면 「인트로…/가사 없음」을 표시하며, 재생을 가리거나 로딩으로 기다리게 하는 일은 없습니다
- 화면 공유 페이지 상단에는 「방 분위기음」 카드, 하단에는 항상 「재생 중」 바가 있습니다
- 연결이 끊겼다가 다시 연결하거나, 나갔다가 다시 입장하면 서버 스냅샷을 다시 반영합니다(중복 제거 키는 "세션 + revision"이며 순수 revision이 아닙니다). 이로써 "사람은 모두 나갔는데 곡이 계속 나오는" 상황을 막습니다

### 2.6 방 · 친구 · 채팅

- 방을 만들 때 이름, 인원 상한(2~8), 선택적 비밀번호를 입력하며, 방 번호는 원클릭으로 복사해 친구에게 공유할 수 있습니다
- 친구: 사용자 이름으로 검색, 신청 보내기, 수락·거절, 온라인 상태, 친구 삭제
- 방 안의 텍스트 채팅은 P2P DataChannel을 사용하므로 서버는 내용을 볼 수 없습니다

### 2.7 테마와 외형

- 6가지 테마: **薄荷汽水**(데스크톱 기본), **青竹**(모바일 기본), 朱砂, 晴空, 蜜橙, **夜航**(데스크톱 권장 배색)
- 사용자 지정 배경화면을 지원합니다. 밝은/어두운 두 가지 바탕에서는 텍스트와 컨트롤 색상이 반전되며, 모두 통일된 팔레트를 사용합니다
- 데스크톱은 프레임 없는 창 + 직접 그린 타이틀 바, 최소 1120×720

### 2.8 로그와 피드백

- 실행할 때마다 로그 파일 하나를 작성하고, 시작 시 7일이 지난 파일을 정리합니다. 설정의 「실행 로그」에서 현재 파일 경로를 바로 보여 주고 「로그 폴더 열기」를 제공합니다
- 네이티브 크래시가 발생하면 크래시 리포트를 추가로 남깁니다(모듈 목록, 플랫폼 스레드 스택, minidump 포함)

## 3. 현재 상태

**이미 쓸 수 있는 것**: Windows 버전은 기능이 완성되어 있습니다(음성, 화면 공유, 곡 신청 스테이션, 함께 음악 듣기, 친구와 방, 테마, 로그와 크래시 리포트). Android도 전반적인 기능이 대체로 사용 가능합니다

**현재의 난관: iOS 빌드와 출시**

코드 레벨에서는 이미 「데스크톱 / 모바일」 두 가지 레이아웃을 분리했고(짧은 변 600dp 미만이면 자동으로 단일 컬럼), Android가 같은 코드로 문제없이 동작하므로 iOS 이식 작업량은 크지 않습니다. 다만 현재 **Apple Developer Program** 계정이 없어 서명도, TestFlight도, App Store 등록도 할 수 없습니다

> **연 99달러의 Apple 개발자 계정을 후원해 주실 분이 있다면 정말 감사하겠습니다.** iOS 버전의 조기 출시를 앞당기고, 이 프로젝트를 "혼자 쓰는 Windows 도구"에서 "세 플랫폼이 모두 있는 셀프 호스팅 제품"으로 발전시킬 수 있습니다. 후원해 주신 분은 후원자 목록에 감사를 표시합니다

기타 알려진 문제:

- **대칭형 NAT / UDP 차단 네트워크에서는 연결할 수 없습니다**: "중계 없음" 아키텍처의 대가이며, 진단과 안내로 사용자가 네트워크를 바꾸도록 유도하는 방법밖에 없습니다
- **일부 MusicFree 플러그인이 클라이언트를 크래시시킵니다**(QuickJS 브리지 계층의 네이티브 스택 오버플로, `0xc00000fd`). 현재는 스레드 스택 확대와 HTTP 동시성 제한으로 완화하고 있으며, 이후에도 계속 디버깅·최적화할 예정입니다
- Android release는 여전히 debug 서명이며 아직 스토어에 올라가지 않았습니다. 지금 설치해 보려면 release에서 apk를 내려받아 수동으로 설치하세요

## 4. 주요 기술과 감사의 말

| 분야 | 사용한 것 |
| --- | --- |
| 실시간 미디어 | **WebRTC**(`flutter_webrtc`) + 자체 개발 메시 구성, ICE restart, 비트레이트 프리셋 제어. DTLS-SRTP 암호화, 미디어는 서버에 남지 않음 |
| 연결 탐색 | 자체 개발 **STUN**(Python 구현, 주소 응답만 수행). 직접 구축하거나 공용 STUN으로 교체 가능 |
| 시그널링 | **FastAPI + WebSocket**, 자체 JSON 프로토콜(camelCase, 기계가 읽을 수 있는 오류 코드, 애플리케이션 계층 ping/pong 하트비트와 시계 동기화) |
| 저장 | **SQLite + SQLAlchemy async**(`aiosqlite`), 계정·친구·방·구독. 아바타는 데이터 볼륨에 저장 |
| 음악 플러그인 | **QuickJS**(`quickjs_engine`) 샌드박스에서 **MusicFree 플러그인** 실행, 호스트가 HTTP / storage / 주요 Web 전역을 브리지 |
| 재생 | **media_kit**(libmpv)로 직링크 재생, LRC 가사 파싱, SNTP 방식 시계 정렬 |
| 오디오 장치 | Windows Core Audio로 마이크 시스템 볼륨 조절, 장치 열거와 핫플러그 |
| 인터페이스 | Flutter 프레임 없는 창(`window_manager`) + 6가지 테마 팔레트, 데스크톱 3컬럼 / 모바일 단일 컬럼 자동 적응 |

### MusicFree에 특별히 감사드립니다

곡 신청 스테이션의 플러그인 생태계 전체는 **MusicFree** 덕분입니다: 플러그인 프로토콜, 플러그인 설치와 버전 규칙, 디렉터리 구조, 검색 결과 표시 방식, 차트와 플레이리스트의 카드 스타일 모두 [MusicFree](https://github.com/maotoumao/MusicFree)와 그 데스크톱 버전 구현을 참고(그리고 맞춰) 만들었습니다

MusicFree의 이 개방적이고 깔끔한 플러그인 규격이 없었다면 이 프로젝트의 곡 신청 스테이션은 "몇 개 플랫폼 API를 내장한" 수준에 머물렀을 것입니다. 저자와 플러그인을 작성하는 모든 분께 진심으로 감사드립니다

> 이 프로젝트는 **어떤 음원도 내장하지 않습니다**. 플러그인은 서버 관리자가 구독 주소로 배포하고 각 클라이언트가 로컬에서 실행합니다. 오디오 요청은 플러그인이 반환한 주소로 클라이언트에서 직접 전송되며 OmiocLink 서버를 거치지 않습니다

## 5. 기여: Issue와 PR

### Issue를 올리기 전에

1. 먼저 기존 issue를 검색해 중복을 피하세요
2. **버전**(`releases`의 파일명에 버전이 있거나 클라이언트 정보 페이지에서 확인), **시스템**(Windows 10/11, Android 버전), **네트워크 환경**(가정용 회선 / 학교망 / 회사망 / 휴대폰 핫스팟, 프록시나 VPN 사용 여부)을 분명히 적어 주세요
3. **가능하면 로그와 크래시 스택을 첨부하세요**. 원격 원인 파악을 쉽게 만드는 유일한 방법입니다

#### 로그 위치와 제공 방법

- 디렉터리: **`%LOCALAPPDATA%\OmiocLink\logs`**(포터블 실행 시 exe 옆의 `logs\`, 휴대폰에서는 앱 전용 디렉터리이며 설정 화면에 전체 경로가 표시됩니다)
- 여는 방법: 클라이언트의 **설정 → 실행 로그 → 「로그 폴더 열기」**. 페이지에서 이번 실행의 로그 파일 경로도 바로 보여 줍니다
- 디렉터리 안의 파일(접두사로 구분):

| 파일 이름 | 무엇인지 |
| --- | --- |
| `client-<时间>.log` | 실행마다 하나, 일반 실행 로그(입장, 시그널링, 미디어, 곡 신청, 오류가 모두 들어 있음) |
| `crash-<时间>-<pid>.log` | **네이티브 크래시 리포트**: 예외 코드, 모듈 기저 주소, 전체 모듈 목록, 크래시 스레드와 플랫폼 스레드 스택 |
| `crash-<时间>-<pid>.dmp` | minidump 전체 스레드 덤프, WinDbg / VS로 바로 열어 호출 스택 확인 가능 |
| `native-<时间>-<pid>.log` | 시작 정보: 이 머신이 실제로 로드한 C++ 런타임 버전("특정 머신에서만 크래시"를 조사하는 첫 단서) |

- 로그는 시작 시 7일이 지난 파일을 자동 정리하므로 **문제가 생기면 최대한 빨리 압축해 두세요**
- 가장 간단한 방법: `logs` 디렉터리 전체를 압축해 issue에 첨부하세요. 서버 주소와 사용자 이름이 들어 있으니 **공개하고 싶지 않은 부분은 올리기 전에 직접 지워 주세요**
- Android 크래시: `adb logcat -s flutter`, 또는 설정 화면에 표시되는 로그 디렉터리의 파일을 복사

### PR 보내기

- Fork → 설명이 드러나는 브랜치 생성 → 이 작업에 필요한 파일만 수정
- 주석은 **중국어**로, 「왜 이렇게 작성했는지」(겪은 함정, 제약의 출처)를 설명합니다
- 클라이언트: `flutter analyze lib test`에 error/warning 없음, `flutter test` 전부 통과. **리포지터리 전체 `dart format`은 실행하지 마세요**(이 리포지터리는 format-clean이 아니어서 전체 포맷팅이 거대한 노이즈 diff를 만듭니다)
- 서버: `uv run pytest`, `uv run ruff check .`, `uv run mypy`가 깨끗해야 합니다
- PR 설명에는 **무엇을 바꿨고, 왜, 어떻게 검증했는지**(어떤 테스트를 돌렸는지, 실기기·실제 네트워크로 확인했는지)를 분명히 쓰고, 검증하지 못한 부분은 솔직히 적어 주세요
- UI 변경에는 **변경 전후** 비교 스크린샷을 첨부하는 것을 권장합니다
