## 1. OmiocLink について

OmiocLink は**自分と決まった友人だけで使う**ためのデスクトップ通話ツールです。インターネットに接続した小さな Linux マシンでシグナリングサービスを 1 つ動かし、何人かの友人がクライアントをインストールすれば、ボイスチャットで盛り上がり、同じ画面を見て、一緒に音楽を聴けます

![ 海报](assets/readme/海报.webp)

2 つの部分から構成されています:

| ディレクトリ | 内容 |
| --- | --- |
| `client/` | Flutter クライアント: Windows デスクトップ + Android。iOS は対応を進めており、協力してくださる方を切望しています |
| `server/` | FastAPI シグナリングサーバー + 独自実装の STUN + Web 管理コンソール。オフライン導入用の compose とイメージ書き出しスクリプトを含みます（[server/README](server/README.md) 参照） |
| `deploy/` | サーバーのオンライン導入で使う compose: Docker Hub のイメージを取得するだけ。導入手順は [server/README](server/README.md) を参照 |

OmiocLink プロジェクト全体には 1 つの設計上の制約が貫いており、すべての機能はその上に成り立っています:

> **サーバーはシグナリングと状態管理だけを担い、メディアを一切中継しません。** 音声・画面・チャットはすべてメンバー間で直接やり取りされます（WebRTC + DTLS-SRTP）。サーバーには**メディア中継モジュールがなく**、TURN も配備しません —— サーバーの通信量は常に KB 単位です

想定している使い方: 2〜8 人の固定メンバーでゲームを遊ぶ、一緒に映画や試合を観る、深夜に一緒に音楽を聴く、友人の画面を遠隔で見る —— しかもそれらのデータがサードパーティのサービスを一切経由しないこと

### 2.1 P2P 通信：メディアはサーバーを通らず、プロキシもリレーもありません

- **メッシュ構成**: 入室すると、各メンバーはルーム内の他の全員と PeerConnection を 1 本ずつ張ります。遅延は 1 ホップだけです。ルームの人数上限は 2〜8 人で、まさにメッシュが最も効率的になる規模です
- **サーバーが中継するのは 3 種類だけ**: SDP（offer/answer）、ICE 候補、ルームとメンバーの状態。いずれも数 KB の JSON で、メディアは最初のフレームから両端間を直接流れます
- **リレーはなく、「通信をプロキシする」という選択肢もありません**: サーバー上に TURN は存在せず、リレープロセスも動いていません。その代償として**ホールパンチングに失敗すれば接続できません**。ネットワーク環境に合わせてお使いください（サーバーで stun モードを有効にすると、設定画面で現在のクライアントのネットワーク種別と利用可否を確認できます）
- **同じ LAN 内なら自動的にローカル通信**: host 候補により、同じ WiFi にいるメンバーは直接接続します。遅延は 5ms 未満、外部への通信はゼロです
- **ネットワークをまたぐ場合は STUN によるホールパンチング**を使います。業界での成功率は約 80〜90%（家庭用ルーターのほとんどはコーンナット）です。対称 NAT（キャリアの CGNAT でよくある）や、UDP を遮断する学内・社内ネットワークでは失敗します
- **失敗もきちんと伝えます**: 入室前に接続性を検査し、つながらないメンバーは画面上で示されます。設定画面の「現在の接続」には**直接接続できているメンバー x/y**、上り/下りのビットレートがリアルタイムで表示され、ホールパンチングに失敗したメンバーがいると、実行可能な対処案（スマホのテザリングに切り替える / 家庭回線を変える / ファイアウォールが UDP を遮断していないか確認する）を示します
- **STUN は自前で立てられます**: `cd deploy && docker compose --profile stun up -d` で、「あなたのグローバル側のアドレスは何か」に答えるだけの STUN が起動します。これもメディアを一切中継しません

### 2.2 ボイス通話

- 入室すると同時にマイクがオンになります。マイク入力にはエコーキャンセル / ノイズ抑制 / 自動ゲイン調整（AEC / NS / AGC）がかかり、Opus でエンコードされます
- メンバーリストでは 1 人につき 1 つのタイルを表示し、発話レベル・接続品質・ミュート状態を確認できます（ミュート状態はサーバーからルーム全員にブロードキャストされます）
- **互いに干渉しない 3 種類のローカル音量**。いずれも自分にだけ影響し、サーバーには送信されません:
  - 音楽の音量（0〜100）
  - メンバーごとの音量（0〜200、`userId` ごとに記憶され、再接続・再入室・再起動後に自動で復元されます）
  - マイクの音量（0〜100、既定の録音デバイスのシステム音量をそのまま操作するもので、「相手に聞こえる自分の声の大きさ」に相当します）
- 出力デバイスは切り替え可能（ヘッドホン / スピーカー）で、デバイスの抜き差しがあると一覧が自動で更新されます
- モバイル版（**青竹**テーマ、短辺 600dp 未満で自動的に 1 カラム + ボトムナビゲーションに切り替え）は同じ通話ロジックを流用し、右カラムをボトムパネルに置き換えているだけです

### 2.3 画面共有

- **モニター全体または単一のウィンドウ**を選択でき（サムネイル付き）、**システム音声の同時共有**も選べます —— 共有しているゲームや映画の音もそのまま相手に届きます（スピーカー再生だと相手側でエコーが聞こえることがあるので、ヘッドホンの使用をおすすめします）
- **エンコード戦略**は 3 段階で、共有する内容に合わせて選べます（既定は「バランス」で、自動的に判断します）:

| プリセット | 適した用途 | フレームレート | 帯域が逼迫したとき |
| --- | --- | --- | --- |
| フレームレート優先 | ゲーム配信 | 60fps 固定（30 を下回らない） | まず解像度を下げ、フレームレートは維持 |
| 解像度優先 | 会議 / 資料 / プレゼン | 30fps から開始し、余裕があれば 60 まで上げる | ソースの解像度を固定し、スケーリングしない |
| バランス | 通常の用途 | 自動（30 / 60） | 平均 QP から画面が高ダイナミックか静止かを判断し、どちらを優先するかを決める |

- **ビットレートは手動調整不要**: 30 Mbps の上り帯域の予算を視聴者数で分割します（2K のソース + 視聴者 3 人なら 1 本あたり約 9 Mbps）。予算に応じて解像度とフレームレートは自動的に段階を下げ、下限は **720p / 30fps** —— ゲーム配信では、ぼやけることよりもフレーム落ちのほうが許容できません

- 視聴側はワンクリックで全画面（Esc で終了）、共有側はいつでも停止・ソース変更ができます
- ルーム画面の右カラムは「画面共有 + チャット + キュー」で、チャットメッセージは **DataChannel**（P2P）を通ります。サーバーはチャットの内容も履歴も保存・中継しません
- Android 版では画面共有を提供していません（`getDisplayMedia` に Android 実装がないため）。マイクのシステム音量調整も未提供の可能性があります

### 2.4 ソングステーション（**MusicFree 互換**）

ソングステーションの音源は内蔵ではなく、**MusicFree プラグインを実行する**仕組みです:

- サーバーが保存するのは**プラグインの購読 URL** だけです。音声と楽曲のメタデータはすべて、**各クライアントがローカルで** QuickJS サンドボックス上でプラグインを実行して取得します —— サーバーは音声の代理取得・キャッシュ・配信を一切行いません
- MusicFree と 1 対 1 で対応する 3 つのビュー: **検索**（上部の検索ボックス、種別 × 音源の 2 段タブ、入力しながら結果を表示）、**ランキング**、**人気プレイリスト**
- 音源ごとに個別のタイムアウト（全音源 2 秒 / 特定音源 8 秒 / ランキング 4 秒）を設定し、3 回連続で失敗すると 5 分間サーキットブレーカーが働きます。失敗はメインの表示を邪魔せず、検索ボックスの隣に「N 件の音源で異常」という小さな入口が出るだけです
- 検索結果は 6 時間ローカルにキャッシュされます。設定画面ではプラグインの有効化・無効化・並べ替え・アンインストール、一括更新、`userVariables` の設定、音質の選択（スムーズ / 標準 / 高品質 / ロスレス）が可能です
- **適切な音源プラグインを導入すれば**、理屈の上では複数のアプリを行き来する必要がなく、ほとんどの音楽を聴けます。実際にどこまで聴けるかは、設定したプラグインの品質次第です

### 2.5 一緒に音楽を聴く（ルーム内の同期再生）

ルーム内の再生は「各自が勝手に再生する」ものではなく、**サーバーを正とする + 時計合わせ**で成り立っています:

- キューはサーバーが保持し、変更のたびにスナップショット全体をブロードキャストします（`revision` は単調増加）。誰が何をリクエストしたか、何番目の曲か、誰が曲を送ったかは、どのクライアントでも同じに見えます
- **再生位置は時計同期に基づきます**: クライアントは ping/pong で SNTP 方式のオフセット推定を行います（RTT が最小のサンプルだけを残し、サーバーの時計だけを信頼します）。「再生を始めた瞬間」から各自が推測するのではありません
- **権限には線引きがあります**: 曲のリクエストは誰でも可能（1 人あたり既定で 88 曲まで）。曲送りができるのはルームのオーナーか、その曲をリクエストした人だけ。キューのクリアはオーナーのみです。クライアントは権限のないボタンを隠すだけで、最終判断はサーバーが行います
- 1 曲終わると自動的に次へ進みます（クライアントが EOS を報告し、サーバーは `revision` で冪等に処理します）
- **再生モードはルーム単位**です: リストリピート（既定）/ 1 曲リピート / 順番再生 / シャッフル。再生/一時停止ボタンの左隣のボタンで順に切り替わり、ルーム内の全員が同じモードを見ています。モードを変えても再生中の曲は途切れません
- 歌詞は LRC のタイムラインに沿って、ローカルの再生位置に合わせてスクロールします。歌詞が取得できない場合は「イントロ…/歌詞なし」と表示し、再生を妨げることも、ローディングで待たせることもありません
- 画面共有ページの上部には「ルームの環境音」カード、下部には常時「再生中」バーがあります
- 切断後の再接続や、退室しての再入室では、サーバーのスナップショットが再適用されます（重複排除のキーは「セッション + revision」で、素の revision ではありません）。これにより「全員が退室したのに曲が鳴り続ける」状態を防ぎます

### 2.6 ルーム · フレンド · チャット

- ルーム作成時に名前・人数上限（2〜8）・任意のパスワードを設定でき、ルーム番号はワンクリックでコピーして友人に共有できます
- フレンド: ユーザー名で検索、申請の送信、承認/拒否、オンライン状態、フレンド削除
- ルーム内のテキストチャットは P2P の DataChannel を通るため、サーバーから内容は見えません

### 2.7 テーマと外観

- 6 種類のテーマ: **薄荷汽水**（デスクトップ既定）、**青竹**（モバイル既定）、朱砂、晴空、蜜橙、**夜航**（デスクトップ推奨の配色）
- カスタム壁紙に対応。ライト/ダークの 2 種類の下地では文字とコントロールの色が反転しますが、いずれも共通のカラーパレットで管理されています
- デスクトップはフレームなしウィンドウ + 自前描画のタイトルバー、最小サイズ 1120×720

### 2.8 ログとフィードバック

- 実行ごとにログファイルを 1 つ書き、起動時に 7 日より古いファイルを削除します。設定画面の「実行ログ」には現在のファイルパスがそのまま表示され、「ログフォルダーを開く」も用意されています
- ネイティブクラッシュ時は追加でクラッシュレポートを書き出します（モジュール一覧、プラットフォームのスレッドスタック、minidump を含む）

## 3. 現状

**すでに使えるもの**: Windows 版は機能が揃っています（音声、画面共有、ソングステーション、一緒に音楽を聴く、フレンドとルーム、テーマ、ログとクラッシュレポート）。Android 版も全体としてほぼ利用可能です

**現在の課題: iOS のビルドとストア公開**

コード側ではすでに「デスクトップ / モバイル」の 2 種類のレイアウトを分離しており（短辺 600dp 未満で自動的に 1 カラム）、Android 版が同じコードで問題なく動いているため、iOS への移植の作業量は大きくありません。現状は **Apple Developer Program** のアカウントがないため、署名も TestFlight もなく、App Store に公開できません

> **99 ドル/年の Apple デベロッパーアカウントを支援してくださる方がいれば、本当にありがたいです。** iOS 版の早期公開を後押しし、このプロジェクトを「自分で使う Windows ツール」から「3 つのプラットフォームが揃ったセルフホスト製品」へと進められます。ご支援いただいた方はスポンサー一覧でお礼を記載します

その他の既知の問題:

- **対称 NAT / UDP 遮断のネットワークでは接続できません**: これは「リレーなし」アーキテクチャの代償であり、診断とヒントでユーザーにネットワークの切り替えを促すしかありません
- **一部の MusicFree プラグインがクライアントをクラッシュさせます**（QuickJS ブリッジ層でのネイティブスタックオーバーフロー、`0xc00000fd`）。現状はスレッドスタックの拡大と HTTP 同時接続数の制限で緩和しており、今後も継続的に調整します
- Android 版の release は今も debug 署名のままで、ストアにも公開していません。いま試したい場合は release から APK をダウンロードして手動でインストールしてください

## 4. 主要技術と謝辞

| 領域 | 採用技術 |
| --- | --- |
| リアルタイムメディア | **WebRTC**（`flutter_webrtc`）+ 独自実装のメッシュ構成、ICE restart、ビットレートプリセット制御。DTLS-SRTP で暗号化し、メディアはサーバーに残りません |
| 接続検出 | 独自実装の **STUN**（Python 製、アドレスをそのまま返すだけ）。自前で立てることも、公開 STUN に切り替えることも可能 |
| シグナリング | **FastAPI + WebSocket**、独自の JSON プロトコル（camelCase、機械可読なエラーコード、アプリケーション層の ping/pong ハートビートと時計同期） |
| ストレージ | **SQLite + SQLAlchemy async**（`aiosqlite`）、アカウント/フレンド/ルーム/購読。アバターはデータボリュームに保存 |
| 音楽プラグイン | **QuickJS**（`quickjs_engine`）サンドボックスで **MusicFree プラグイン**を実行し、ホスト側で HTTP / storage / 一般的な Web グローバルをブリッジ |
| 再生 | **media_kit**（libmpv）で直リンクを再生、LRC 歌詞の解析、SNTP 方式の時計合わせ |
| オーディオデバイス | Windows Core Audio によるマイクのシステム音量調整、デバイス列挙とホットプラグ |
| UI | Flutter のフレームなしウィンドウ（`window_manager`）+ 6 種類のテーマパレット、デスクトップは 3 カラム / モバイルは 1 カラムに自動適応 |

### MusicFree への特別な謝辞

ソングステーションのプラグインエコシステム全体は **MusicFree** の功績です: プラグインプロトコル、プラグインのインストールとバージョン規則、ディレクトリ構造、検索結果の見せ方、チャートとプレイリストのカードスタイルは、いずれも [MusicFree](https://github.com/maotoumao/MusicFree) とそのデスクトップ版の実装を参考に（そして合わせて）作られています

MusicFree のこの開かれたクリーンなプラグイン仕様がなければ、このプロジェクトのソングステーションは「いくつかのプラットフォーム API を内蔵した」レベルで止まっていたでしょう。作者とプラグインを書くすべての方に心から感謝します

> 本プロジェクトは**音源を一切内蔵していません**。プラグインはサーバー管理者が購読 URL で配布し、各クライアントがローカルで実行します。音声リクエストはプラグインが返したアドレスへクライアントから直接送信され、OmiocLink サーバーを経由しません

## 5. コントリビュート: Issue と PR

### Issue を立てる前に

1. まず既存の issue を検索し、重複を避けてください
2. **バージョン**（`releases` のファイル名にバージョンが含まれます。クライアントのアバウトページでも確認できます）、**システム**（Windows 10/11、Android のバージョン）、**ネットワーク環境**（家庭回線 / 学内ネットワーク / 社内ネットワーク / スマホのテザリング、プロキシや VPN の有無）を明記してください
3. **可能な限りログとクラッシュスタックを添付してください**。遠隔での原因調査を楽にする唯一の方法です

#### ログの場所と提供方法

- ディレクトリ: **`%LOCALAPPDATA%\OmiocLink\logs`**（ポータブル版は exe と同じ場所の `logs\`。スマホではアプリのプライベートディレクトリで、設定画面にフルパスが表示されます）
- 開き方: クライアントの **設定 → 実行ログ → 「ログフォルダーを開く」**。ページ内にも今回の実行のログファイルパスがそのまま表示されます
- ディレクトリ内のファイル（接頭辞で判別）:

| ファイル名 | 内容 |
| --- | --- |
| `client-<时间>.log` | 実行ごとに 1 つ。通常の実行ログ（入室、シグナリング、メディア、選曲、エラーがすべて入っています） |
| `crash-<时间>-<pid>.log` | **ネイティブクラッシュレポート**: 例外コード、モジュールの基底アドレス、全モジュール一覧、クラッシュしたスレッドとプラットフォームのスレッドスタック |
| `crash-<时间>-<pid>.dmp` | minidump による全スレッドダンプ。WinDbg / VS で直接開いてコールスタックを確認できます |
| `native-<时间>-<pid>.log` | 起動情報: このマシンが実際に読み込んだ C++ ランタイムのバージョン（「特定のマシンだけ落ちる」を調べる最初の手がかり） |

- ログは起動時に 7 日より古いファイルを自動削除するため、**問題が起きたら早めにまとめてください**
- 一番簡単な方法: `logs` ディレクトリ全体を圧縮して issue に添付してください。サーバーアドレスやユーザー名が含まれるので、**公開したくない部分は投稿前にご自身で削除してください**
- Android のクラッシュ: `adb logcat -s flutter`、または設定画面に表示されるログディレクトリからファイルをコピーしてください

### PR の提出

- Fork → 内容が分かるブランチ名を作成 → その変更に必要なファイルだけを編集
- コメントは**中国語**で、「なぜそう書くのか」（踏んだ罠、制約の由来）を説明してください
- クライアント: `flutter analyze lib test` で error/warning が出ないこと、`flutter test` がグリーンであること。**リポジトリ全体の `dart format` は実行しないでください**（本リポジトリは format-clean ではなく、全ファイルの整形は巨大でノイズだらけの diff を生みます）
- サーバー: `uv run pytest`、`uv run ruff check .`、`uv run mypy` がクリーンであること
- PR の説明には、**何を変えたか、なぜか、どう検証したか**（実行したテスト、実機・実ネットワークで確認したか）を明記し、未検証の部分は正直に書いてください
- UI の変更には**変更前と変更後**の比較スクリーンショットを添付してください
